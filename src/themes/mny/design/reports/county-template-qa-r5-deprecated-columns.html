Why this is a sweep, not a restatement

The R5 rows cannot answer this question on their own

1. R5’s definition excludes half the question. The class is “Deprecated column bound but not rendered”, so a deprecated column that is shown was never enumerated. Asking “which components still show a deprecated column” against the R5 rows would return zero by construction, not by fact.

So this report starts from the sections R5 names and sweeps each for every deprecated column it binds — a column whose live source title carries (Delete) or deprecated. R5 rows are joined onto that sweep by column name — not by the title text.

Of the deprecated columns the sweep found, 0 are ones R5 does list, but under a title the source does not carry — the name join is what recovers them. Each is paired back to its Likely Fix ID and marked unconfirmed, never merged silently. 0 are columns R5 does not list at all.

2. R5’s “hidden and not filtered” claim is not reliable. Applying the class found components carrying active filters on the very column the report calls unfiltered. The likely cause is a config-shape blind spot: a v2 component keeps filters in a top-level filters key, a v1 component has no such key at all and uses dataRequest.filterGroups — so a check written against filters is vacuously true for every v1 component. The same mistake that hid half the pattern from the T6 fetch-mode scan.

Here filters are found structurally — any config object whose col is this column, wherever it lives — and an empty value is reported as an inactive filter rather than an active one.

Every other mention of the column name in the payload is reported too, because a splice out of columns[] is index-safe but not reference-safe. Source-schema snapshots (externalSource.columns, sourceInfo.columns, and outputSourceInfo.asUdaConfig.sourceInfo.columns on components that are themselves consumable as a source) are excluded — they describe the source, not the binding, and they legitimately list the deprecated column.
