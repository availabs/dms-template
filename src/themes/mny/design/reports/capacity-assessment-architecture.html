The question

One wide table,
or two that talk to each other?

Two datasets are now in view: the 1.0 county capability self-reports (2,354 rows, 169 jurisdictions, irregular coverage per town) and the 2.0 statewide capability catalog (649 rows, 402 real programs). Both are being folded toward one 2.0 schema. Before that conversion locks in a shape, the capacity assessment needs a home — and there are exactly two candidate designs:

Option A — extra columns. Add Availability / Adequacy / Interest-Need fields directly onto the existing capability rows. Option B — a separate dataset. A dedicated capacity table, one row per jurisdiction per capacity item, joined to the capability data when a report needs both.

The two prior reports already contain the evidence to answer this. This report walks through that evidence, then grounds the answer in how DMS actually models datasets and joins — per src/dms/skills/live-cross-view-joined-section.md and uploading-gis-and-tabular-datasets.md.

The short answer

Two datasets.
One shared key.

Capability data is sparse and event-sourced — rows appear when something is reported. Capacity needs to be dense and complete — one row per jurisdiction per item, always. Those are two different table shapes, not one with a few extra columns.

Join them live at report time on (jurisdiction, capability/capacity-type name) — never merge them into one table.

Why Capability Rows Can’t Host Capacity Columns

Three pieces of evidence, all already verified in the prior reports.

1 · No reliable row to attach to

Breadth per jurisdiction runs 1 to 5 domains (of 5). 21 of 169 jurisdictions touch only one domain; even the single jurisdiction that reaches all 5 (Mamakating, Sullivan) has just 26 capability rows — nowhere near the ~30 discrete items a capacity assessment rates. There is no row sitting there waiting for capacity columns in the other 4 domains.

2 · The failure mode already happened

The 2.0 catalog shows exactly what happens when a fixed, complete vocabulary gets merged into a table built for irregular real entries: 245 of 649 rows (38%) are bare placeholders carrying a name and nothing else. Forcing a capacity grid onto the capability table reproduces that same shape — at a much larger scale.

3 · Capacity must cover silence, not just presence

The Capabilities vs. Capacity report's core finding: a jurisdiction with zero capability rows in a domain is exactly the case capacity assessment needs to resolve. Columns on capability rows can only ever describe jurisdictions that already have a row — the opposite of what’s needed.

Put numerically: a complete capacity grid needs 169 jurisdictions × ~30 items ≈ 5,070 rows. The capability table currently holds 2,354 rows, unevenly spread, with 21 jurisdictions contributing a single row each. Even ignoring everything else, the row counts alone don’t line up — because they’re answering two different questions with two different shapes.

Two Different Table Shapes

Capability dataset Capacity dataset
Row shape Irregular — a row exists only when a jurisdiction reports one Complete — one row per jurisdiction × per fixed capacity item
Cardinality today 2,354 rows across 169 jurisdictions (1–26 rows each) 169 × ~30 ≈ 5,070 rows (target, once built)
What a missing row means Nothing reported yet — genuinely ambiguous (absence vs. not asked) Shouldn’t happen — every cell gets a value, incl. “Not Reported”
Update trigger Event-sourced — a new plan, program, or role is adopted Cyclical — a rapid self-report survey, re-run on a cadence
Value shape Free text + a handful of optional narrative fields 3 fixed enums per item (Availability × Adequacy × Interest/Need)

This is the same distinction the HoC 1.0→2.0 conversion work already solved once, for a different hazard grid: build the master jurisdiction list once, then expand it into a complete jurisdiction × item grid, with an explicit “Not Reported” placeholder rather than a missing row. The same technique — not the same table — is the right model here.

How The Two Join Without Exploding

DMS can bind a single Card/Spreadsheet section to two views joined live, in-engine — no duplication, no manual sync. The mechanics come straight from live-cross-view-joined-section.md, with one gotcha that applies directly here.

1

Same query engine. The join compiles to one SQL statement against a single backend — both the capability and capacity tables need to live in the same engine (e.g. both Postgres) to be joined live at all.

2

Pin the composite key, or it fans out. The skill's core gotcha: an unpinned join key multiplies every base row by however many matching rows exist on the other side. Joining on jurisdiction alone would multiply every capability row by all ~30 capacity items for that jurisdiction — a 12-row town would explode to 360 joined rows. Pin the key to (jurisdiction, capability/capacity-type name) instead, so each capability row matches exactly its one corresponding capacity rating.

3

Declare the joined source's schema. sourceInfo.columns is required on the joined view or the section's edit mode crashes outright — a real schema array, not left implicit.

Composite join key

capability.jurisdiction=capacity.jurisdiction
capability.type_name=capacity.item_name

e.g. a “Hazard Mitigation Plan” capability row joins only to the “Hazard Mitigation Plan” capacity row for that same jurisdiction — not to the other 29 capacity items.

One Jurisdiction Identity, Not Two

The Hazards-of-Concern 1.0→2.0 conversion already resolves every county + jurisdiction to a canonical GeoID via a geoid-crosswalk reference sheet — including the gnarly cases (villages straddling two counties, NYC’s five boroughs, duplicate/mis-cased jurisdiction rows). Capability and capacity should key off that same crosswalk, not a second identity system built from whatever county text happens to appear in each CSV. Get this right once and all three 2.0 datasets — Hazards of Concern, Capability, Capacity — join cleanly on the same jurisdiction key forever after; get it wrong and every future join needs its own one-off name-matching pass.

Recommended path

Build capacity as its own dataset, joined by key

1 · Build the full grid

Every jurisdiction × every one of the ~30 capacity items, always present — “Not Reported” is a value, never a missing row.

2 · Key it to the crosswalk

Same GeoID crosswalk as the Hazards-of-Concern conversion, so jurisdiction identity is consistent across all three 2.0 datasets.

3 · Join, don’t merge

Bind reports to both views live via a pinned (jurisdiction, type) composite key — two datasets, one query, no fan-out.

Net effect: the capability table keeps its natural sparse, event-sourced shape; the capacity table gets the complete, uniform coverage the assessment actually needs; and a report that wants both side by side — a capability row next to its capacity rating — gets it from a live join, not a fragile shared row.
