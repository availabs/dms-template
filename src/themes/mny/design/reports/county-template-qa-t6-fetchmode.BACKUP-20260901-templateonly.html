Half the data components were never in this catalog

“Friday’s task closed with ‘99 in scope, 99 correct, 0 outstanding’. That number reproduces exactly — and it is complete only over components stored in the v2 config shape. Components still stored in v1 were invisible to the scanner, because it selects rows that bind an externalSource, and a v1 row keeps its snapshot under sourceInfo instead.”

Confirmed and corrected. The template runs two generations of element-data at once and migrateToV2.js:203-226 is the authority on which is which: v2 stores its source under externalSource, v1 under sourceInfo (with dataRequest.filterGroups for filters), and dataWrapper/index.jsx:220 migrates either one at mount — so both render, and neither is broken. What broke was the census: scan_fetchmode.mjs selected on externalSource alone, so every v1 component fell out of the catalog before any rule was applied, and a sweep that had genuinely finished its rows reported completeness over a target it could not see all of.

Nothing about the rule or the write path changes. migrateV1ToV2 copies display across verbatim (stripping only filteredLength, invalidState, hideSection), so a v1 component honours a stored fetchMode exactly as a v2 one does, and apply_element_data_key.mjs sets display.fetchMode without caring which shape the row is in.

Any count that does not say which shapes it covered is not yet a count. Every table in this report now carries a Config shape column for that reason, and the same assumption should be checked in the other scripts in scripts/report_fixes/.

The rule this report applies

external source →  Smart (fetch on change)
internal source→  Force (always re-fetch)

External sources are DAMA sources reached through a pgEnv (hazmit_dama); their content changes on a publication cycle, so Smart re-fetches when the query changes and otherwise reuses the cache. Internal sources are DMS-managed datasets in this app; an author can edit a row and expect to see it, so Force re-queries every mount.

With fetchMode absent the loader falls back to readyToLoad === true ? 'smart' : 'cache' (dataWrapper/useDataLoader.js:245–247), so an unset component already behaves as Smart wherever readyToLoad is true — invisibly, and only by accident of a second setting. Stored fetch mode is what an author sees in the panel; Resolved behaviour is what the browser does. A fix is judged against the stored value, because that is the thing that is missing.

The scope this rule is applied within

Force re-queries on every mount, so each component set to it is page-load cost. The sweep is therefore limited to the datasets an author actually edits and expects to see change. A component is fixed only when:

  • the data source is one of Actions_Revised, Capabilities_Catalogue, Hazards_of_Concern, Jurisdictions, Participation, Roles
  • the page is one of the 26 labelled Relevant in county-template-qa-t5-requirements-v2.xlsx

The other 874 components are deferred, not dropped: they keep their Fix ID and carry the reason, in the Deferred - out of scope sheet and the appendix below. Nothing about them is broken — they keep resolving through the implicit fallback exactly as they do today.
