The fixes, and what they prevented

closed

1 · Mitigation measures on every hazard page

Before

15 of 16

  • Categorised through a column the data steward had renamed “Category-Deprecated” — displayed and used as the filter
  • Each stored 249 rows: the statewide measures catalogue, not the county's
  • Six columns, older configuration format
  • No warning anywhere — every component stored the pre-deprecation title

After

16 of 16

  • Retired column unbound everywhere
  • 11 rows each — scoped to the hazard the page is about
  • Five columns, current format, all sixteen identical
  • Verified section by section on 1 Sep
Implication of leaving it

The measures inventory is the evidence a plan offers for its mitigation strategy. Every hazard page was presenting the same 249 statewide entries, so the hazard-specific analysis a reviewer expects was not hazard-specific at all. Separately, a retired column is retired because it is going to be removed — when that happened, all fifteen tables would have failed at once, on every county built from this template, with no prior signal.

closed

2 · Protection on shared state plan narrative

Before

377 / 398

  • 21 narrative cards carried no restriction at all
  • 1 more appeared protected but named no user and no group — it granted nothing
  • 2 carried an extra individual grant nobody had recorded
  • Concentrated on flooding (6), hurricane (4), ice storm (3)

After

398 / 398

  • All restricted to the LHMP Template Editor group
  • Value taken from the 374 existing cards, not assumed
  • Every write verified: one field changed, placement untouched
  • Independently re-counted afterwards: 0 remaining
Implication of leaving it

This narrative is shared state content, not county content. An unrestricted card can be edited by any county author, and there is no review step between that edit and the text other counties inherit. The exposure was 5% of the shared narrative, sitting on the highest-traffic hazard pages. The card that looked protected but granted nobody anything is the more instructive case: it would have passed any audit that checks whether the setting exists rather than what it says.

closed

3 · Mapping the plan to its federal requirements

Before

308

  • 308 sections carried no 44 CFR 201.6 tag, so no part of the plan could be traced to the requirement it satisfies
  • 67 of them were empty leftovers that should not have been on a page at all
  • No way to tell a section that needed a tag from one that could never have one

After

307 / 308

  • 167 sections tagged against the requirement they satisfy
  • 67 empty components removed from their pages
  • 56 ruled genuinely not applicable, on the record rather than by omission
  • 1 left open pending a decision on which requirement applies
Implication of leaving it

Requirement tags are what let the plan be audited element by element from the site itself, rather than by someone reading the whole thing and cross-referencing by hand. Untagged, the county has no defensible way to show a reviewer which page satisfies which federal element. The 67 removals matter for a second reason: an empty, untitled section on a live page is indistinguishable from a broken one, and every county built from this template inherited all 67.

closed

4 · Sections that were showing nothing, or a fraction of the county

Before

0 · 12

  • Hazards Impacted By Climate Change returned 0 rows — a blank table on the climate change page
  • Planning Participants returned 12 of the county's participants
  • Jurisdictional Annex links resolved by place name instead of by id, so annex links did not reach the right record

After

17 · 106

  • Climate change table returns 17 hazards
  • Participants table returns 106 — nearly nine times the previous figure
  • Annex links resolve by id again; the table serves all 22 jurisdictions
Implication of leaving it

These are sections whose content existed in the database and was not reaching the page. A blank hazards table reads as “this county assessed no climate hazards”; a participants list showing 12 of 106 understates the planning process a plan is required to evidence. Neither announced itself — both rendered cleanly, just with the wrong content, which is the hardest class of defect to notice from the outside.

closed

5 · Making data refresh behaviour explicit

Before

0

  • No component stated how it should refresh; each inferred it from an unrelated setting
  • Components on author-edited datasets could serve a cached view
  • Some were explicitly set to the wrong behaviour
  • The first sweep reported this complete while covering only half the template

After

132

  • All 132 components on the six author-edited sources set to always re-fetch
  • The 33 the original sweep could not see are now included
  • Rule recorded: internal data re-fetches, external data caches
  • Only 2 remain unset, both control types with no such setting
Implication of leaving it

These are the datasets authors actively edit. Without an explicit refresh setting a component can show an author the version of the data that existed before they edited it — which reads as the edit having failed, and invites it being entered a second time. The last 33 were the ones the original sweep had been blind to: they sat behind a “complete, 0 outstanding” result that was measured over half the template, and would not have been found by re-running it.
