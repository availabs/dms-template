The premise

The platform already voted. This direction finishes the count.

Every recent workflow investment moved data entry toward the plan: the /actions pattern with its jurisdiction picker, workspace, and "Back to Plan" card; the six-page county-actions design flow; the hazards-of-concern and critical-infrastructure form prototypes hidden inside the template; the annex page that renders N jurisdictions from one page of URL state. Meanwhile the counties themselves demonstrated the paradigm planners understand — Suffolk drafted 163 annotation slots without once needing a training course, because the work sits where the plan is.

Direction B makes that the rule: every record a county enters is entered from inside the county site, next to the display it feeds. The one genuinely open question is what happens to the state's side of the panel — kept as a slim console (B1, recommended) or fully retired (B2). Both variants are specified below.

The planner's day, after

1Open Plan Status on your own site: "Flooding chapter: 3 slots left · Fallsburg: 2 hazards without an action."
2Click the gap. Land on the worklist already filtered to it — same site chrome, county name still in the corner.
3Fix the rows inline, or open one record's edit page. Save. The chapter's table updates, because it was always the same data.
4Back on the chapter, the card that showed the gap now shows the number. Nothing to publish for data; narrative still goes through draft → publish.

The word "admin" never appears. Neither does a second app.

The architecture call that makes this cheap: "in the plan" means in the county's URL space — not in the county's cloned pattern

The current-state report documents real clone drift: Westchester and Suffolk carry frozen 71-section annex snapshots while the template grew to 91; the prioritize workbench never reached any clone; every clone still hardcodes Sullivan's geoid on its homepage. Copying form pages into 60+ county patterns would multiply that failure mode.

The platform already has the answer running: shared patterns mounted on every county subdomain. The /actions pattern (and /admin itself) are subdomain: * — one set of pages, visible at suffolk_draft.…/actions and every other county, scoped per county by URL params and the per-subdomain geoid filter sets. Form surfaces built this way are maintained once, themed like the plan, breadcrumbed into the plan's chapters — and immune to clone drift. The county's own pattern keeps what genuinely belongs to it: narrative, annotations, page IA. Its chapters just link into the shared surfaces with their scope in the URL.

Section 02

B1 or B2: what happens to the state's side

B1 · Slim DHSES console ← recommended

/admin stops being a planner surface and becomes a ~12-page, DHSES/AVAIL-gated console — honestly named, one audience, one job: run the program.

  • • Status board — all 62 counties: plan status, expiration, fill %, form coverage (the cross-county twin of the plan's status page)
  • • Review queue — actions/records pending state QA (approvable, comment fields already in the data)
  • • Catalog stewardship — LHMP_IA, Mitigation Measures, R&V Matrix, Policies, Content Resources, Funding Sources, Jurisdictions, NYS Dams
  • • Imports — bulk CSV in/out (nothing replaced Action Upload)
  • • Ops — web analytics, DHSES Running Fixes

Why keep it: DHSES needs one place to see all counties; catalogs need a steward's UI; QA needs a queue. Those are real, current functions with data behind them.

B2 · Retire the pattern entirely

Everything B1 keeps must find another home:

  • • status board → the statewide MitigateNY site (it already tracks county plan status publicly)
  • • catalog stewardship → the generic datasets-pattern tooling (a CenRep-style data manager)
  • • QA queue → per-county, on each plan's status page (state reviewers visit the county's site)
  • • imports → dataset tooling upload

Honest assessment: workable, but it trades a purpose-built console for generic tooling, and DHSES loses the single cross-county operational view unless the statewide site absorbs it properly. Higher operational risk for modest extra simplification — B2 is the end-state to grow into if the B1 console turns out to be little-used, not the first move.

Section 03

The honest costs, and how each is handled

Cost / risk Handling
Role-gating inside county sites — who may edit which columns, where already precedented in the data: per-county HMP Admin groups exist on every draft; the annex page is DHSES-gated for edit today; the county-actions design expresses role as column ownership per page (jurisdiction owns local priority + gaps; county owns county priority). Formalize that convention rather than inventing new auth.
Clone drift — form pages must not fork per county solved by the shared-pattern architecture (see callout above): form surfaces live once, on subdomain: * patterns, scoped by URL. County patterns keep only narrative + links. The county-identity defect Report 1 found (Sullivan geoids hardcoded in every clone) argues for the same fix on the template's own pages.
Edit-mode overwhelm — chapters already show ~74 sections, 58% of them untouchable data components entry bands must not add clutter: one compact "Edit the data behind this table" affordance per display cluster, opening the worklist — not more inline spreadsheets on the chapter. (This is also the argument for keeping full worklists on their own shared pages.)
Publish-lag confusion — form data is live, narrative is draft→publish say it in the UI, once, at the entry band: "Records save immediately and appear wherever this data is shown. Page text stays draft until you publish." The status page reads draft_sections so drafted narrative counts as progress.
Biggest build of the three end-states sequenced so every phase ships stand-alone value (below); roughly half the surface already exists as live mechanics or approved designs, and the actions live-build is already a tracked task.
