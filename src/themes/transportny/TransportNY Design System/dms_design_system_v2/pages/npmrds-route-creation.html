01

Two ways to build the same list

A route is an ordered array of TMC codes and nothing else. Both modes write that one array, so a route is never “a marker route” or “a click route” downstream — the report, the comparison and the map all see the same thing. The modes differ only in how many clicks it costs you to fill it, and in what happens when you come back to edit.

TMC click default · shipped

Click a segment to add it; click it again to remove it. The click is a queryRenderedFeatures hit-test against the shapefile layer, so what you can select is exactly what the tiles draw at the current zoom.

  • ·Order is click order, not geographic order. The array is appended to; nothing re-sorts it. A route clicked out of sequence graphs out of sequence.
  • ·Search-to-add covers the segments a click cannot reach — a TMC you already know, or one buried under an interchange. Nine characters, and the code must resolve to real geometry before Add lights up.
  • ·Remove last pops the tail; Clear all empties the array. Both exist in both modes — the port originally shipped them for markers only.
Markers · auto-routing shipped · with caveats

Drop two or more waypoints and the path between them is map-matched to a TMC sequence. Drag a waypoint and the whole path re-resolves. For a 40-segment corridor this is two clicks instead of forty.

waypoint gradient · first → last
  • ·The resolved list is editable. Auto-routing fills the array; the TMC list is the same list, and rows can be removed after the fact.
  • !Markers do not survive a save. Only tmc_array is written, so a marker-made route reopens as a TMC-click route with no waypoints. Editing it means editing segments, not dragging pins. Persisting points is a known open item, not an oversight to design around.
  • !One network vintage. The match runs against 2022_v0_6_0, pinned. A live test found only 2020–2022 resolving near Albany, so the year is a chip, not a select, until the usable range is re-verified.

02

Saving — three fields, one row

The save dialog is deliberately short. The old tool asked for a folder and a start/end date and time; this one asks for a name, a description and tags, because a route is a geometry — the report that uses it owns the time window, and one route feeding two reports with two different windows is the normal case, not the exception. Tags aren't free text either: they're validated against the same agency:/user: vocabulary Reports uses, with one-click suggestions for the viewer's own login groups.

New-route state differs in three places only: the title reads Save new route, the red overwrite line is absent, and the confirm button reads Save. Nothing else moves — same fields, same order. One exception, tags-specific: a brand-new route seeds its own user/agency tags already committed (solid chips, not dashed suggestions) — the suggestion state drawn above is what an already-existing route shows, because it predates auto-tagging and the seed effect only ever fires once, at creation.
