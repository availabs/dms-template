Data Manager API.

The read API every dashboard renders from: one graph endpoint, a path grammar under the uda root, and an options object that filters, groups and orders. This page is the lookup for the paths, the options and what returns without a token. It assumes you have run the quick start.

How a request is made

The API is a Falcor JSON Graph endpoint. A Falcor request is a list of paths into one large graph; the response is the part of the graph those paths touch. You send the list as a URL-encoded JSON array in the paths query parameter of the graph route, with method=get.

GET https://graph.availabs.org/graph?paths=<url-encoded JSON array of paths>&method=get

→ { "jsonGraph": { "uda": { "<env>": { … the values at your paths … } } } }

Three rules follow from that shape. The options object is itself a JSON string inside the path array, so it is encoded twice: once as JSON, once as a URL. A value that is an object, a date or a null is wrapped as {"$type":"atom","value":…}; unwrap it. And the response keys are your attribute strings exactly as you sent them.

Environments

The second path segment names a data environment. npmrds2 is the platform's environment: every dataset with a datasheet in Measures & Data lives there, and the worked example calls it "the database being pulled from". An environment written app+instance, with a plus sign, is a site-managed dataset rather than a platform table; the server classifies by the plus sign. The datasheets do not use that form.

Sources and views

A source is a dataset; a view is one version of it, and data is always read by view. The source page in Data & Downloads and the datasheets carry the ids. These paths list them.

PathReturns
["uda", env, "sources", "length"]The number of sources in the environment.
["uda", env, "sources", "byIndex", {from, to}, [attributes]]Sources in index order, each a reference to sources.byId; attributes are resolved through the reference.
["uda", env, "sources", "byId", id, [attributes]]Attribute values for one source. Attributes the site itself reads: name, display_name, type, categories, description, update_interval, statistics, metadata.
["uda", env, "sources", "byId", id, "views", "length"]How many views the source has.
["uda", env, "sources", "byId", id, "views", "byIndex", {from, to}, [attributes]]The source's views in order, each a reference to views.byId.
["uda", env, "views", "byId", id, [attributes]]Attribute values for one view: version is the version name; metadata carries the column list and the download url map.

Rows

Row reads hang off viewsById and always carry an options string, even an empty one. Ask for the length first; a range past the end returns nothing for the missing indices.

PathReturns
["uda", env, "viewsById", view, "options", options, "length"]The count of rows that match the options. With groupBy, set aggregatedLen to get the count of groups.
["uda", env, "viewsById", view, "options", options, "dataByIndex", {from, to}, [attributes]]The matching rows from index from to to inclusive, one key per attribute.
["uda", env, "viewsById", view, "options", options, "byIndex", {from, to}]References to dataById for the matching rows, for tables that carry an id column.
["uda", env, "viewsById", view, "dataById", id, [attributes]]One row by its id.

The options object

A JSON object, serialised to a string, placed after options in the path. Keys are column names. The first seven rows are the documented grammar; the rest are keys the server accepts today, with what the code does.

OptionMeaningExample
filterKeep rows whose column is any of the listed values. The strings "null" and "not null" in the list test for a missing or present value."filter": { "geoid": [36001, 36002], "status": ["active"] }
excludeDrop rows whose column is any of the listed values; the same null words apply."exclude": { "year": [2011, 2012], "status": ["inactive"] }
gt · gte · lt · lteGreater than, greater than or equal, less than, less than or equal. One number per column."gt": { "loss": 15000 }
likePattern match on the column as text, case-insensitive. Supply the wildcards yourself: % is any run of characters, _ one character."like": { "name": "John%" }
groupByGroup by these columns or positions. Attributes then need an aggregate for every non-grouped column."groupBy": ["geoid", "status"]
orderBySort; the value is the sort order. The worked example uses "desc nulls last"."orderBy": { "geoid": "desc", "status": "asc" }
aggregatedLenWith groupBy, make length count groups rather than rows."aggregatedLen": true
havingClauses applied after grouping, joined with and."having": ["count(1) > 10"]
normalFilterA list of { column, values } objects, merged into filter before the query runs. The worked example sends it empty."normalFilter": []
metaPer-column lookup instructions that replace coded values with labels. Accepted; this page does not document its grammar."meta": {}
keepOriginalValues · isDama · fnAccepted by the server. isDama makes a plus-sign environment read as a platform table. The other two are not documented here.—

Conditions across keys combine with and. Blank values and the null words are stripped from the SQL parameters, so an empty list is the same as no condition.

Attributes

The last path element on a row read is the list of columns. Each entry is a column name, or a column name followed by as and an alias, or an expression with an alias. The response key is the attribute string as you wrote it: ask for "event_id as event_id" and that is the key you read. The datasheet's schema table lists the real column names; the API does not validate them for you.

["event_id", "facility as road", "count(1) as events"]

Sign-in and what returns without a token

Reads of a published view work without a token; the worked example carries none. The server reads the Authorization header as the sign-in token and otherwise treats the request as the public user. Sources carry permission levels, so a signed-in request may see sources the public listing does not; this page does not promise which. Row data is never editable through this API. A source's or a view's description and metadata can be updated with a token that carries edit authority on that source; that path is for administrators and is not documented here.

The legacy form

The 2025 reference was written with the root dama and the casing viewsbyId and databyIndex. Those routes remain in the server code and the options object is the same; the uda root supersedes them and is the form the site itself uses. The 2024 appendix's three one-line APIs, NPMRDS, PM3 and RIS, are superseded by these pages. Write new code against uda.

legacy  dama[env].viewsbyId[view].options[options].length
        dama[env].viewsbyId[view].options[options].databyIndex[{from,to}][attributes]
current uda[env].viewsById[view].options[options].length
        uda[env].viewsById[view].options[options].dataByIndex[{from,to}][attributes]

Limits

  • No OpenAPI or Swagger document exists. This page is the reference.
  • No rate limit is published. The data server's code sets none; a limit at the proxy is not documented here.
  • No maximum page size is documented. The site reads its own lists in pages; do the same, and always after a length call.
  • Column names are not checked against the schema before the query runs. A wrong name is a failed request, not an empty column.
  • Numbers can arrive as strings, as "cost": "78062" does in the worked example. Parse them.
