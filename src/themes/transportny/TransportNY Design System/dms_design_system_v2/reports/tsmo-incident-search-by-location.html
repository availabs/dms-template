// scoping recommendation

Searching incidents by location.

The Incident Search explorer already finds any TRANSCOM event by region, county, year, month, category and keyword. Adding “on this piece of road” to that list is a smaller job than a new page — but it is not a one-line job, because the page is bound to a source that does not carry a usable TMC column. This report says what the change actually is, what it will and will not be able to answer, and whether lat/long search is worth building after it.

The recommendation in one paragraph.

Add a TMC facet to the existing Incident Search page rather than building a second explorer. Implement it as a live cross-view join — Transcom Event TMC (1635/2799) ⋈ Transcom Events (956/1947) on event_id — which is a configuration change to the existing sections, not new component code, and is already a documented pattern (skills/live-cross-view-joined-section.md). Both views live in npmrds2, so the same-engine constraint is satisfied. Then set expectations honestly on the page: it will answer how many crashes, how long they lasted, how much delay they caused on a segment. It will not answer how many people were hurt, because nobody populated that field.

// 03

Three ways to get a TMC filter, in ascending order of cost.

option A
Filter tmclist in place
~1 hour not recommended

Literally one more facet on the page as it stands: an OR group of like leaves on tmclist, one per selected TMC — the exact shape the keyword box already uses (skills/full-text-search-filter.md). No join, no new source.

Why not: tmclist is null on half the table, and where it is populated it disagrees badly with the snapped table (§04). It is also substring matching on a delimited list, so a longer TMC code that contains a shorter one as a prefix will produce silent false positives. It would ship a filter that looks authoritative and is not. Worth keeping in mind only as a stopgap if the join turns out to be blocked.

option B
Join 2799 ⋈ 1947 on event_id
~1–2 days recommended

The TMC facet filters the snapped table; every column the results table and KPI strip already display comes across the join from the events table. This is a configuration change to the existing sections — the top-level join key in each section's element-data, alias-prefixed columns (ds.tmc, meta.estimated_duration_mins) — not new component code, and it stays a live fetchMode:'smart' binding with no seeding. The worked precedent is the TSMO Corridor View's time-space speed grid, which joins npmrds 982 ⋈ meta 983 the same way.

Four things to get right, all of them already written down in skills/live-cross-view-joined-section.md: both views must be the same query engine (both are Postgres/npmrds2 — satisfied); sourceInfo.columns is required or /edit crashes the page; pin the metadata version column or the join fans out; and write engine-correct SQL. One extra note specific to this join: the grain changes. 2799 is one row per event×TMC, so a results table built on it needs count(distinct event_id), not count(1) — §05 shows a case where that is a 75 vs 57 difference.

option C
Materialise a wide incident×TMC view in the ETL
ETL work

Push the join upstream: a new DaMa view, one row per event×TMC, carrying the incident detail columns alongside tmc. The page then binds to one source and every section gets simpler and faster. This is the right long-term answer if TMC-scoped incident analysis becomes a routine ask rather than a one-off. It is not the right first move — build option B, see whether the page gets used, then decide.

What the facet itself looks like — no new primitive needed.

A TMC facet is the same Filter control as Region and County: operation:'filter' with isMulti:true, writing a tmc page variable. One caveat the existing facets do not have: there are 36,621 distinct TMCs, so an unscoped DISTINCT option list is not a dropdown anyone can use. Scope it the way the page already scopes County — cascade the option query off the current region/county selection (columns[].filters style, which is what the existing builder uses precisely because it narrows the DISTINCT scan) — and let the control's type-ahead do the rest. A user who arrives with a TMC code in hand types it; a user who does not picks a county first and gets a list they can read.

Why this matters more than it looks.

Whichever linkage the page uses becomes the definition of “an incident on this segment”, and the two definitions differ by a factor approaching two on individual segments. Some of the gap is explained — the snapped table has no 2019 or 2020 — but not all of it, and the 120-12145 row (5 snapped vs 7 self-reported, 2 in common) is not explained by coverage at all.

Recommendation: build on the snapped table (it is the one with a documented method and the one that carries delay), state on the page which linkage is in use and over what years, and file the reconciliation as a separate data ticket rather than letting it block the feature. Do not silently union the two — the union is the right thing for a one-off export like the CSV in §05, where a human reads the linkage column, and the wrong thing for a page that publishes a count.

The honest answer to the question behind the request.

You wanted total crashes, injuries and fatalities on these segments. Crashes: 4 distinct incidents over 2015–2025, and even that is a floor, because it is the union of two disagreeing linkages and the snapped table skips 2019–20. Injuries and fatalities: the data cannot answer this. Not “zero” — unrecorded. TRANSCOM's feed populates injury_involved on 0.018% of all events statewide and fatality_involved on 0.005%, and every non-null value in both columns is true, which is the signature of a flag that is set when someone happens to note it and left null otherwise. There is no denominator.

If injury and fatality counts are the actual goal, this is the wrong dataset and the recommendation changes shape: the NYSDOT crash file (ALIS / CLEAR) is the system of record for injury severity, and the work becomes joining that to the TMC network rather than adding a facet to this page. Worth deciding before the TMC filter is built, because it changes what the page is for.

// 06

Lat/long search: the input is bad UI, the capability is not.

You asked whether a person would ever search by lat/long, and whether that is just bad UI. Short answer: typing coordinates into a box is bad UI — nobody knows their coordinates, a typo is undetectable, and a single point is not a query. But “find incidents near here” is a good question, and the data supports it today.

the good news
99.996%
of events are geocoded

point_lat / point_long are non-null on 3,836,753 of 3,836,903 events, on the source the page already reads. wkb_geometry matches. (Ignore event_location_latitude — 82 rows.)

the better news
0
lines of new code required

The filter engine already supports gte / lte leaves on arbitrary column expressions. Both a bounding box and a true radius were run live against prod while writing this report.

Measured, 2026-09-14, against the live prod uda route.

A bounding box is four numeric leaves. The ::numeric cast is load-bearing — point_lat is stored as text, so an uncast comparison sorts lexicographically and returns nonsense. 

// bbox around the four NY 146 TMCs — 161 events, 8 of them crashes
{ op: "AND", groups: [
  { col: "point_lat::numeric",  op: "gte", value:  42.68 },
  { col: "point_lat::numeric",  op: "lte", value:  42.72 },
  { col: "point_long::numeric", op: "gte", value: -74.18 },
  { col: "point_long::numeric", op: "lte", value: -74.02 },
]}

A radius is one more leaf — a haversine expression, bounded by a bbox first so the index does the work. Results scale as they should: 117 / 340 / 885 events at 1 / 3 / 5 miles around (42.70, −74.03). 

// …plus the four bbox leaves above, which bound the scan
{ col: "(6371000*2*asin(sqrt(power(sin(radians(point_lat::numeric-42.70)/2),2)
        +cos(radians(42.70))*cos(radians(point_lat::numeric))
        *power(sin(radians(point_long::numeric-(-74.03))/2),2))))",
  op: "lte", value: 1609 }   // metres — 1 mile

One dead end worth recording so nobody retries it: st_distancesphere(wkb_geometry, …) and wkb_geometry::geography both fail with “Only lon/lat coordinate systems are supported in geography” — the geometry column does not carry an SRID the cast accepts. Wrapping it in st_transform(st_setsrid(…,3857),4326) works but is slower and buys nothing over haversine on the two numeric columns.

pattern 1
Map-extent search — “search this area”
best practice

The user pans and zooms; the map's viewport is the bounding box; a “search this area” button writes four page variables and the table reacts. This is the interaction every mapping product converged on (Zillow, Airbnb, Redfin) for a reason: the user never types a coordinate, the query is always well-formed, and the extent is visible rather than remembered. The coordinates should still appear in the URL, because that is what makes a result shareable — but as output, not input.

Cost: the page already has a map placeholder in its results band. Making it real is a Map section plus the four page variables above, and the zoomToFilterBounds machinery already exists. The genuinely new part is map→filter write-back — today's sections read page variables, they do not write extents into them — which is the one real platform enrichment in this whole report, and it would benefit every map on every TransportNY page.

pattern 2
Click-a-point + radius
good

Click the map (or geocode an address, or drop on an intersection), then a radius chip — ¼ mi / ½ mi / 1 mi / 5 mi. This is the right shape for “what happens around this interchange”, which is a question people actually ask. The radius must be a small set of presets, not a free number: a slider invites a user to discover that 0.3 miles returns nothing and 0.4 returns everything, which reads as a broken tool rather than a sparse road.

pattern 3
A lat/long text box
only as a paste target

Your instinct is right — as a primary input this is bad UI. It fails on discoverability (nobody carries coordinates), on error tolerance (a transposed digit lands in Ohio and looks like “no results” rather than a typo), and on the fact that a bare point answers nothing without a radius the box does not collect.

It is worth roughly twenty lines as a secondary affordance, because one real workflow exists: someone has a coordinate pair from a crash report, a GPS trace, or a colleague's email, and wants to paste it. Accept a single permissive field — 42.7059, -74.0354 and the DMS/DDM variants — drop a pin, recentre the map, and hand off to pattern 2. It is a navigation control that moves the map, not a filter that queries the table. That distinction is the whole design.

The sequencing point.

Lat/long search and TMC search answer different questions and should not be built in the same pass. Spatial search finds the incident where it was reported — a point, ungeocoded to the network, which is what you want for “what happened near this intersection”. TMC search finds the incident where it caused delay — a network segment, which is what you want for corridor analysis and what ties back to NPMRDS. A crash at a ramp terminal is spatially at the ramp and operationally on the mainline. Build TMC first (it is the one with a stated purpose), then map extent, and keep them as two facets a user can combine rather than one merged “location” control.

What this deliberately does not recommend.

A second Incident Search page pre-filtered to a fixed TMC set. The filters are page variables in the URL, so a saved link like ?tmc=120-12145,120-12146,120%2B12146,120%2B12147 is that page, for free, for any TMC set anyone ever wants — no build, no maintenance, and it stays correct when the underlying page improves. A duplicated page would be a fork that goes stale the first time the original changes. If the corridor deserves a permanent home, the right artifact is a bookmark or a link from the Corridor View, not a page.

A custom React component for any of this. Every recommendation above is a filter leaf, a join key, a theme token or a page variable — author-reachable surface. The single exception is map→filter write-back (step 4), which is a platform capability rather than a one-off, and which every future map page inherits.
