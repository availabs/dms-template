Rebuilding the TransportNY documentation.

The platform now has three products on one origin and a documentation site that still describes one of them — the legacy one. This report audits what is at devtny.org/docs, inventories what the three products actually expose, reads every ticket users have filed to learn where they get stuck, and reviews how documentation should be done and how eleven comparable platforms do it. It ends with one recommendation for the shape of the documentation and the full page tree it should contain, including how the docs plug back into the product pages.

2
pages already show what good looks like — published 2026-08-28

The Macro View guide (280612) and Measures & Methodology (281670) are task-ordered, single-sourced from the code's own measure definitions and provenance record, and carry dated, state-captioned screenshots. The rest of the site should be brought to their standard, not the other way round.

the recommendation in one paragraph

Keep one public documentation site at /docs, reachable without a login and from every product's navigation. Organise it by domain — Get started · NPMRDS · TSMO · Freight Atlas · Measures & Data · Developers · Admin — and nest the documentation types (start here, how-to, screens & settings, FAQ) inside each product hub. The owner's instinct to separate "how to use the tools" from "how the numbers are made" is right and is what every framework asks for on the page; but because LOTTR, TTTR, excessive delay and the shared datasets are used by NPMRDS and TSMO, the methodology must live once, in a shared hub with a fixed per-measure template, and be summarised (two or three sentences plus a deep link) on every tool page that shows the number. Retire the legacy-site pages into a dated, frozen branch; delete the empties and strays; give every page a last-reviewed stamp and an "applies to" badge; and turn the ticket system's resolved questions into the FAQ.

what is wrong — structurally
  1. Two UI generations, one nav, no label. Nine legacy pages ("mousing over the 'Add New' button … Folders") sit beside two new ones ("the right panel", "the download builder") with nothing to say which site each describes.
  2. Single-product framing. The hub is "Transport NY Documentation" but the NPMRDS root opens "Welcome to the … (NPMRDS) Platform"; TSMO is introduced inside the NPMRDS Quick Start.
  3. Definitions in five places, drifting. LOTTR "for cars only … exclude trucks" (Quick Start) vs "Stream — all vehicles" (Measures); two different TTI formulas under one name; a TED entry pasted from Truck TED.
  4. Naming collisions. PM3 = the federal measure set, the legacy dashboard, the site's analytical fork, and a data type; Macro Tool / Macro View / Regional Analysis / Region Analysis name one thing; TTI is an index and an institute on one page.
  5. Audience mixing. End-user how-tos, planner whitepapers, a case study with stock art, an internal runbook, an internal product memo and code-level API notes share one tree at equal weight.
  6. Draft artefacts published. "(Draft)" in five section titles; "Coming Soon" in eight places (one for a feature that shipped); editor-mode /docs/edit/… URLs as links; 24 links to slugs that no longer exist; one malformed https://https//.
  7. No provenance except on the two new pages. The 2024 layer states no sources; the Freight Atlas page states that it guessed.
  8. Unreachable from the products. No product nav links to /docs; the new pages link to other tools by name without URLs.
what is good — carry it forward
  1. Measures & Methodology (281670): federal-vs-analytical distinction first; seven measures on a fixed five-part template; the "which delay measure" decision table; coverage eras; the two cross-year traps; glossary — every figure traced to PROVENANCE.md / precision.js / downloadManifest.js.
  2. Macro View guide (280612): task-ordered, six real screenshots each captioned with the state that produced it and its capture date.
  3. The FAQ's 19 questions (280326): the right planner questions; only the answers' tool names are stale.
  4. Template walkthroughs Snapshot · Seasonality · Bi-directional, each Introduction → Setup → Interpretation, with the "check TMC lengths before concluding" caveat.
  5. Graph-type reference + measures table (281503): 13 visualisations defined; units/sources/equations per measure incl. the off-peak free-flow window.
  6. Composite Score Tutorial: a tool-independent Excel method (30 % reporting filter, min–max normalisation, weighted rank).
  7. What is NPMRDS / strengths and weaknesses primer (225868).
  8. Admin guides: Uploading Data, Managing Data (authority levels 1/2/10, events log), Map Editor style controls, publish-to-page steps, the map21/pm3/pm3_aggregate runbook.

How documentation should be done: separate doing from knowing on the page, never at the top of the site.

Frameworks (Diátaxis, DITA, Information Mapping, Google and Microsoft style guides, Write the Docs, Every Page is Page One), usability research (Nielsen Norman Group, Meng et al.), public-sector content design (GOV.UK, ONS, plainlanguage.gov, 18F, Section 508 / WCAG), and how statistical publishers document methods (BLS, Census, ONS, Eurostat, FHWA TPM guidance; Datasheets for Datasets, Data Cards, FAIR, DCAT). principles we adopt · structure and writing
  1. A page is a task, a lookup, or an explanation — never a blend (Diátaxis). Mixing degrades both halves.
  2. Label hubs by domain, nest the types inside (Meng et al.; Diátaxis on complex hierarchies).
  3. Every page is page one: state what it is for, whom it assumes, and link to neighbours — readers arrive from search or from the app (Baker).
  4. Task pages: goal in the title, prerequisites and location first, one action per step, ≤ 12 steps, expected result, UI labels verbatim (Google, Microsoft).
  5. Plain language even for engineers; precise terms explained in place and linked to one glossary (ONS, GOV.UK).
  6. Two levels of disclosure: summary in the tool, full method one click away; tooltips carry hints, never essentials (NN/g).
  7. One canonical definition, rendered everywhere; duplicated copies drift (Write the Docs). The audit found exactly this failure.
  8. FAQs only from real questions, in the users' words, pruned (NN/g) — the ticket system supplies them.
  9. Descriptive link text, never "Learn more"; deep-link from the app to the specific anchor, not a landing page.
  10. Adopt incrementally; never publish empty sections (Diátaxis: "horrible"). Nine empty pages today.
principles we adopt · methodology, accessibility, operations
  1. Methodology follows the statistical-agency template, identical on every measure page; every calculation step cites its authority (23 CFR 490, FHWA HIF-18-040) and states its edge rules.
  2. Document data products like datasheets: motivation, composition, collection, preprocessing, uses, distribution, maintenance; provenance, licence, cadence are metadata fields, not prose (FAIR, DCAT).
  3. Version methodology independently of the UI and keep old editions (Census D&M, HPMS Field Manual, EPA MOVES); numbers should carry the methodology version they were computed under.
  4. Public change notes for substantive changes; release notes for humans, grouped Added / Changed / Deprecated / Removed / Fixed, dated (GOV.UK, Keep a Changelog).
  5. HTML first; PDF only as a tagged export (GDS, Section 508). WCAG 2.1 AA is the floor: alt text on every screenshot, data tables for complex images, real captions plus transcript for any video (ADA 2024 web rule applies to a state DOT).
  6. Screenshots only when they save words: cropped, annotated with overlays, alt-texted, captured from the real tool with the state named, regenerable (Google style; the design system's assets/screens convention already says this).
  7. Search and navigation together; instrument both — zero-result searches are the content backlog.
  8. API docs = generated reference + hand-written quick start, concepts, recipes, pinned versions, changelog (OpenAPI; Stripe).
  9. Named owners, review triggers, docs reviewed in the same pipeline as the product (Write the Docs; Google SWE book). Docs owned by nobody rot on schedule.

patterns that recur among the strong examples
  1. Two layers, one click apart, per product. INRIX's Overview / Metrics / User Guide triad; TomTom's "How it works → Definitions" nested inside the user guide; Replica's Overview / Sample / Schema / Methodology dataset template.
  2. Methodology is public even when the tool is not. StreetLight gates help but publishes metric-by-metric methodology and validation; Replica publishes 15k words; FHWA publishes step-by-step procedures. Methodology is a credibility asset for procurement, peer review and federal reporting.
  3. A metric page has a fixed anatomy: plain definition → formula → percentile / threshold → time-period rules → source and version → assumptions and caveats → where it appears in the UI.
  4. Change logs cover data and map versions and state the impact. INRIX tells users saved routes get "[Manual Review Required]"; StreetLight re-runs old analyses to show the delta; TomTom stamps release date + software version.
  5. Use case → tool → tutorial → deliverable template (RITIS): answers "how do I produce the MAP-21 / corridor / bottleneck report my boss wants", which no metric page does.
  6. Contextual help from the exact report to the exact explanation — PeMS's "About This Report" beside every report title is the model.
  7. Video supplements, never replaces, text. RITIS's undated, transcript-less videos and INRIX Signals' one-video "user guide" are the weakest how-to experiences reviewed.
  8. Q&A is the natural form for "why does my number differ" — FHWA's Urban Congestion Report documentation, INRIX Map Updates, TomTom FAQ.
what to copy · what to avoid

Copy. Replica's dataset page template and summary-vs-extended methodology pair; StreetLight's public methodology-update posts that quantify impact; RITIS's use-case chain and deliverable templates with real agency samples; INRIX's metric pages (formula + threshold + assumptions) and its map-update Q&A; PeMS's contextual "About This Report" and glossary pathways; TomTom's release date + version stamps; Waze's revision table atop a spec; Esri's in-topic TOC, callouts, related links and feedback footer; HERE's deep-linkable page per output field.

Avoid. Login-gated help that breaks search results and partner deep links (RITIS, StreetLight); PDF-only manuals (ClearGuide v2.08, PeMS 2020) — no search, no deep links, copy-paste errors survive; "Confidential" stamped on a public document; form-gated PDFs; three vendors' UIs for one product; a single ever-growing release-notes article; a version number as a category name; disabled nav tabs; undated pages.

The opening TransportNY has. The incumbent for NPMRDS analytics exposes no public glossary, metric definitions, release notes or API reference. A public, versioned, citable Measures & Data hub — which the 281670 page already prototypes — is the differentiator, and it is what MPO consultants and FHWA reviewers can actually cite.

Cite by title on every PM3 page: FHWA "General Guidance and Step-by-Step Metric Calculation Procedures…" (HIF-18-040), "Computation Procedure for Travel Time Based and Percent Non-SOV Travel Performance Measures" (HIF-18-024), the Average Vehicle Occupancy factors memo, and 23 CFR 490 subparts E–G.

measure page anatomy · identical on every measure
  1. Header block (the "telescope") — name, abbreviation, one-sentence definition, unit; authority (23 CFR 490 §, FHWA guidance by title); methodology version + effective dates; last reviewed; owner; data vintages and coverage; where this appears (tools, reports, API fields); intended and out-of-scope uses. This block is the single source for every in-app summary.
  2. What it answers — the answers string, verbatim from measures.js.
  3. How it is computed — numbered steps, formula with every variable expanded (ticket 2195606), percentile, time bins, stream, aggregation and weighting, rounding.
  4. Parameters and edge rules — thresholds with source; missing data; truck fallback; facility types; minimum sample bars; the 20-mph floor.
  5. The choices made, and why — the section that exists nowhere user-facing except 281670; from PROVENANCE and the task record.
  6. How much to trust it — precision band, minimum-n, share of network clearing it; comparison to the federal value and expected differences.
  7. Worked example — one segment, one period, reproducing a value visible in the tool.
  8. Known limits, comparability across years/versions, revision log, reproducibility (download or API sketch), references, related measures.

The 281670 catalogue entries already follow parts 2–6 on a five-part template; this anatomy adds the header block, the worked example and the per-page revision log, and gives each measure its own URL so the app can deep-link to it.

house rules the tickets wrote
  • Say the basis with every number: geography (statewide / region / county / MPO), period (annual PM3 / monthly series / selected year), vehicle class, system.
  • "Statewide" is a label, never a blank. Blank filters read "All".
  • No internal names on user pages: no "v2 series", "methodology v2", view or table ids, "ClickHouse".
  • Expand every formula variable on first use.
  • Product names verbatim: "Freight Atlas", not "Atlas"; "NPMRDS data" or "travel time data"; "Data freshness".
  • Partial years are labelled partial; series start dates are stated as dates, not slogans.
  • Every headline figure carries a provenance line (source, base year, plan page).
  • Design-language kickers (// 01) stay in the design system; docs pages use plain headings.
screenshots, media, accessibility
  • Screenshots only where they save words; from the real tool, captioned with the exact state and capture date (the assets/screens convention, already proven on 280612).
  • Annotate with overlays, never baked into the PNG; crop; no PII; alt text that states the meaning; complex figures get a data table.
  • Capture scripts stored beside the images so a UI change regenerates them; a stale screenshot is a documentation bug.
  • Video only as a supplement, under ~3 minutes, with corrected captions and a transcript; never the only form of the steps (RITIS is the counter-example).
  • HTML first; PDFs only as tagged exports. WCAG 2.1 AA in review: heading order, alt text, link text, contrast. The 2024 ADA web rule applies to a state DOT.
  • Descriptive link text; deep links to anchors, never "Learn more" to a landing page.
single-sourcing and governance
  • One registry of definitions: measures.js strings, PROVENANCE figures and the download manifest's MEASURED block render into the measure pages; the tool shows the page's header summary. When a number appears in two places it traces to one measurement.
  • Owners: one per hub; a methods owner per measure/data page; a product owner per tool page. UI changes that touch a documented surface touch (or explicitly waive) the doc.
  • Review triggers: tool pages on every release of the surface + a quarterly sweep; methodology pages on every data vintage, TMC network year, FHWA guidance change and the annual PM3 cycle — with a log entry even when nothing changed.
  • Stamps: last reviewed · applies to (product generation / methodology version) · owner, on every page. Substantive edits get a public change note; typos are silent.
  • Feedback loop: the ticket modal on every page; auto-stamped reporter, page and environment; a "Question" category; resolved questions become FAQ candidates weekly; zero-result docs searches are the backlog.

Integrating the docs into the product sites: from the nav, from every number, and back again.

Documentation nobody can reach is the audit's eighth structural problem and the tickets' second cluster. Ten integration points, ordered from cheapest to most involved; the first four are configuration, not code.

  1. A Docs entry in every navigation. Landing (Platform group), npmrds_sub, tsmo2, Freight Atlas v2 and the freight_data datasets nav each get a Docs item that lands on that product's hub (/docs/npmrds, /docs/tsmo, /docs/freight_atlas). The NPMRDS mockups already place it as a QuickLink below the section items; follow that. Landing footer links become real: User guide → /docs/start, API guide → /docs/developers, Data dictionary → /docs/measures_and_data, What's new → /docs/whats_new (all four were dead, ticket 2197781).
  2. A documentation card on each product home. The NPMRDS home design has it ("New here? 1 Build a route · 2 Put it in a report · 3 Read the measure" plus the page list). Repeat the pattern on TSMO home and Freight Atlas home with their hubs' pages; the landing's documentation card lists the seven hubs.
  3. "How it's computed →" on every KPI and measure card resolves to a measure page anchor. /docs/measures_and_data/measures/<measure>#how_it_is_computed. This is the PeMS "About This Report" pattern and directly answers 2191403 / 2214480, which were dead affordances because the destination did not exist. The TSMO home, congestion, reliability, incidents and work-zones cards; the NPMRDS home §01 measure rows and §04 KPIs; the MAP-21 compliance cards; the Macro View right panel (already links methodology →).
  4. A "?" beside every filter bar and legend. TSMO tone bars → /docs/tsmo/filters; Freight Atlas legend blocks → /docs/freight_atlas/layers#<layer>; MAP-21 period toggle → …/concepts/peak_periods_and_epochs; Region selects → …/concepts/geography; the Add Graph value select → the measure glossary; the download builder → /docs/npmrds/macro_view/download. Tooltips carry the one-line hint; the link carries the substance.
  5. In-product methodology surfaces become summaries of the canonical pages. TSMO's Data & Methodology page keeps its role as the product's trust layer, but each measure card renders the canonical page's header block and links to it; NPMRDS home §05 "About the data" and Freight Atlas About do the same. One definition, rendered in four places; every rendering carries "where this appears" back-links.
  1. Stamps on every docs page. A small header component renders applies to (NPMRDS · TSMO · Freight Atlas · legacy site · methodology version), last reviewed, owner from page fields; legacy pages carry a banner. Until the legacy site retires this badge is the only thing that stops a reader following Folders instructions on the new site.
  2. Report an issue / ask a question on every product page. The Page-QA Add-ticket modal already writes to sitemgmt_tickets; surface it in the user menu of each product (RF2174076), auto-stamp reporter · page · environment (56 rows were unattributed), add a Question category, and route resolved questions to the FAQ pages. /docs/help links to /status for known issues (RF2172533).
  3. Search. A search box on the docs home and on each hub; the product Docs item passes the product as a scope. Log zero-result queries — they are the content backlog.
  4. Pattern mechanics. Keep npmrds_docs 1411813 at */docs — it is already reachable from every subdomain and path mount. Restructure the tree (hub pages as parents; reparent surviving children; new slugs), retire old slugs with redirects — the platform has subdomain-level retirement (retired_subdomains) but page-slug redirects need a check and, if absent, a small core addition (escalate per the primitive-change rule). Scope the sidebar to the current hub (the pattern's sideNav is the page tree; hub depth keeps it short). Give every heading a stable anchor id so deep links survive edits.
  5. Screenshots pipeline. The design system's assets/screens convention (real tool · state named · overlays) feeds the live build's image path (/img/npmrdsv5/…); keep one capture script per docs page so a UI release can regenerate its figures, and treat a stale screenshot as a ticket.
