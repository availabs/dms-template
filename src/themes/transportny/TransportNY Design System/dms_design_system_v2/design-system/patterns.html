Data-freshness strip

The brand's consistent “as of” signal, and one of the patterns easiest to lose because it reads as per-page chrome. Two sizes, one vocabulary: a one-line strip in the page header on every working page, and a promoted section on a category landing page where currency is the headline. Both are metaSM with a status dot; the current, complete value is inked, the qualifiers stay muted. Live on all six NPMRDS pages (npmrds-home.html § 01) and on tsmo-home.html § 03.

Three labelled facts, each a mono label over a displayXS value, divided by hairlines: what data you have (a labelled date range, not a bare one — the label is what makes a reader understand it is the system's extent rather than decoration), how much of it, and what network it is on. The network vintage must track the latest data year — showing a 2025 map beside 2026 data is a silent staleness bug, and the count really does move (2024: 52,029 · 2025: 52,157 · 2026: 52,473). A page carrying this row does not also carry the one-line freshness strip above — saying it twice, six inches apart, is what this variant exists to stop. Live on npmrds-home.html. Product counts (reports in the library, saved routes, region count) deliberately do not belong here — they are not data facts, and each belongs to the section that owns it. This variant is a data-driven Card, not authored text — extent, volume and vintage are calc columns on the data itself, so the row cannot go stale. On ClickHouse the whole row is one query in ~0.02s even against a 14-billion-row table: min(date)/max(date)/count() are answered from part metadata when the date column feeds the partition key. Authoring these as static strings is the mistake this note exists to prevent.

Search-first index with facet chips

What to build instead of a paginated everything-table once a collection passes a few hundred rows. Search is the page's primary control, not a column filter: a Filter with operation:'like' writing searchParamKey:'search', plus an OR group of like leaves — one per searchable column. Facets are URL-bound page-variable toggles; an empty leaf drops out of the query, so “no chip” means “no constraint”. Chips read their state back off the URL, which is what makes a result set shareable. Live on npmrds-reports.html (869 rows).

Two placements, one control. Inline — the card below — when the collection is the page. In a dialog when the page's first job is something else (creating, say) and finding is the second: a slim trigger row in the header group opens a modal section group (isModal: true + modalParamKey + modalSize:'4xl') holding this same Filter plus a result list — the trigger is a static Card cell with a click_publish provider whose paramKey equals the group's modalParamKey (modal-section-group.md). Three consequences to design for, not around: the open flag is an action param and never reaches the URL, so a shared link arrives with the query live and the dialog shut — the closed trigger must report the query and its facets, with one click to reopen; the dialog does not paginate, it shows the top matches, scrolls, and states in its foot how many it withheld; and a modal only behaves as a modal on a published page (in edit mode the group renders inline, which is how authors reach it). Live on npmrds-reports.html — § 04 there is a state-driver card that puts the real dialog into each state, which beats drawing four pictures that can drift from the component.

Map workbench · controls left, context right

A full-bleed Map section in a workbench LayoutGroup with group.full_width:'show' — both halves are required, the variant alone still caps at the brand width. Everything else floats over the canvas: controls top-left, context top-right (what the measure means, its unit, its formula, the distribution of the values actually on screen, the legend breaks, and last a get-to-a-segment group — the search plus any jump-to lists), chrome bottom-left, download bottom-right. The split is filter vs. select: a control that changes what the map draws goes left; a search that picks one feature out of what is already drawn goes right, with the other affordances that end at a popup. Panel chrome is the shipped component's, not invented: w-80 · rounded-lg · bg-white/95 · a light h-10 header (bg-zinc-50/80, title text-sm font-medium text-zinc-700) — see ComponentRegistry/map/map.theme.js. Reference prose stays in ordinary content bands below the fold, not in a panel.

Ordering inside the controls panel: the always-on filters first, then the measure selector with its dependent controls in the same tinted band, placed last so the tint runs to the panel's bottom edge (border-t only — a bottom border doubles the panel's own). The band is grey, not brand amber: bg-zinc-100 + border-zinc-950/15, group label text-zinc-600 against the zinc-500 of ordinary control labels. Amber was tried here and is too loud inside a dense panel — and it competes with blue-600 for meaning. Keep a control panel to one colour, and spend it on selection. Grouping is then carried by surface, border and label weight, which is what those are for. Splitting the measure from its own controls to opposite ends of the panel — an earlier revision of this pattern — makes the dependency invisible and is what this replaces. Live on npmrds-macro.html and freight-atlas-map.html.

Report canvas · rail + graph-card grid

A page whose sections all bind to one selection held in a rail. Where the rail comes from: it is the page's side content region — the “Show Content Sidebar” page setting plus the sidebar section group — not a grid column, and it has two named styles: the default card rail and flush (no padding, hugging the content's left edge, full tab height) for a rail that drives the canvas. Both, their wrapper reference and the two requirements flush puts on a page (Full Width band; header as a section in the content column, so the header is no longer full width) are in layouts § 09 and components § Content Sidebar. Where its controls come from: a control rail earns two default buttons — one per half of the job, here Add Route and Add Graph — and each opens a picker modal that gathers a selection and hands it back without writing; everything per-item waits inside the row's open-out, two affordances at most in the row itself. That page is interactive — the rail, both modals and every per-route control are live there, because a control surface and a two-step picker can't be judged from a still; its § 03 keeps only what interaction can't carry (what each control writes, and the rules). The rail may host authored content beside the component; the rail↔canvas column split lives in the pages theme (pages.sectionGroup), not in the shared layoutGroup, and the wrapper must be items-stretch — not items-start — or the rail column collapses to content height and its inner sticky has no room to pin (adding-an-in-page-nav-rail.md is explicit; an earlier revision of this sentence had it backwards and the mockup's rail was measurably inert). Wrap all rail blocks in ONE sticky container — two siblings each pinned at the same top overlap. The graph card: one-line header — title in cardTitleSM (15/500, rendered sentence-case; sentence-case is a legal text-transform modifier, so no new token) · quick-control pills · kebab — no section title above it; legend below the plot, left-aligned, never in the right gutter; exactly one muted attribution line, truncated not wrapped. Live on npmrds-report.html.

14

Preview plate · the shape of a report

A card that offers a report — a template to start from, or a finished example to read — carries a 4:5 plate tile at 1/4 of the card width, on the left, with the text to its right. It answers “how much report is this, and what's in it” before a word is read. Size is the whole trick: the first cut ran the plate full-width above the text at 16:10 and it dominated the card, pushing the description below the fold and stretching the band to twice its necessary height — the legacy home page's 64px tile had the proportion right all along. The mono line under the title names the mix, truncated with a title tooltip (the tile carries the same tooltip). Content, in preference order: a captured thumbnail image cell when one exists at usable resolution → a layout-derived shape drawn from the report's own section grid → the “no preview” tile. The legacy NPMRDS thumbnails are real but are 50 × 50 px base64 PNGs (measured), which is a 64px tile, not a plate — so the shape is today's default and a re-capture is an escalation, not an assumption. Row lists get no plate: a 56px chip beside a title you already know earns nothing. Grouping: past about six cards a flat shelf stops being scannable — split it into typed sub-sections, each a col-span-12 lexical head (numeral · name · rule · count, then one or two lines on when to reach for that type) followed by its cards as siblings in the same band grid. A full-width section forces the next row, so the groups separate themselves with no nesting (contract: a wrapper that contains sections is a band, not a section). The head's copy is also what lets each card's description stay about the template rather than about the family, and it retires the per-card category chip. Live on npmrds-reports.html (16 plates).

View toggle · swap content in place proposal

Two peer views of one collection (a template shelf vs. a filtered table of the same library) sharing one header — clicking a two-way toggle swaps which content band renders below it, with no route change and no page remount. Today this pattern's toggle is a plain link between two pages (npmrds-reports.html ↔ npmrds-reports-list.html); this entry documents the in-place alternative and is not yet built — see npmrds-reports-combined.html for the working mockup and its full expressibility note.

The closest native mechanism already exists, aimed at a different result. sectionGroup.jsx's isModal + modalParamKey gate (the same one modal-section-group.md §6 documents for the search dialog) already mounts/unmounts a whole band based on pageState.filters, set by a Card click_publish provider, with no URL navigation — exactly this pattern's requirement. It falls short three ways: the gate checks whether the param is present, not what it equals (no N-way switch); the open state always renders as a bg-black/50 overlay (no inline/in-flow variant); and action params are deliberately in-memory only, so a specific view can't be bookmarked or shared as a link. Proposed smallest enrichment (not built): two additive keys beside isModal — displayMode:'modal'|'inline' (default 'modal', so every existing group is unchanged) and condition:{searchKey,equals} evaluated against any pageState.filters entry, URL-synced or action. No new registry entry, no bespoke component — the same author-facing config shape an author already uses for the search dialog would build this page: one URL-synced view page filter written by two toggle cells, two content groups with displayMode:'inline' and opposite condition values. A real side benefit over the static mockup: an unmatched group renders null, so only the visible band's sections would ever fetch — no double-fetching the template grid and the paginated table on every load.
