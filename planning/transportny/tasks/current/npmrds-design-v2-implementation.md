## The single report page — active scope

`npmrds-report.html`/`.js` is a genuine second-pass redesign (Phases 9-14, all dated 2026-08-05) of `ReportRouteList` / `RouteRow` / `RouteTagBrowserModal` / `AddGraphModal` — real UX changes, not a reskin. The mockup is itself a transcription of a real live page (`npmrds_sub` pattern, page `2195810`, "NY-9D Beacon Signal Study"), stress-tested with extra cards borrowed from two other real reports.

### Layout
- Rail becomes a **fixed 340px flex sibling** of the canvas column (not a grid column — `col-span-3`/`col-span-9` was explicitly rejected in the mockup's own comments), `sticky top-0 h-svh`, no padding, full tab height. Theme key `pages.sectionGroup` needs a second named style ("flush") beyond the current single 302px style. **Decision 2 (below): use the design's named-style approach** — Ryan's own stashed core change (`sidebarGroup.width` on `sectionGroup.jsx`, prototyped the same day, 2026-08-05) is not being merged.
- No breadcrumb band on this page (deliberate — makes the rail's `sticky top-0 h-svh` math exact; a breadcrumb strip would need to offset both `top` and height).
- Page header is **not** a full-bleed band — it's a card-styled section inside the content column: kicker+meta (region/county/agency, a "published" pill) → h1+purpose → an action stack (Data/Share/Print/Edit) → a full-width freshness footline. Dynamic enough (edit-mode-aware action, multi-sibling-field kicker meta, a computed freshness line) to justify a **second custom component**, per Ryan relaying Alex's suggestion (2026-08-06). Proposed name: `ReportPageHeader` (exact name TBD), alongside `ReportRouteList` as this page's two custom components.
- Compact 64px SideNav on this page (340px rail + 256px expanded nav would starve the canvas).
- Container width: `max-w-[1480px]` (an earlier draft used 1600px — a critique must-fix normalized it back to the catalogue's standard 1480; port 1480).
- Graph-card contract (header shape, legend-below-plot not floating, one-line attribution, size-4 tick/legend collapse) is real polish work, continuous with `report-page-redesign.md`'s existing gap 03 (card visual/density polish) — track as a continuation there, not duplicated here.

### Constraints any redesign must respect (from `ReportRouteList/README.md`, all still binding)
- RRL never writes into a graph section's row (read-only discovery via `findSelfBoundGraphs`)
- key graph/route identity by `trackingId`, not `id` (the orphan-cleanup race fix, 2026-08-03)
- never set the generic `hideInView` flag on this component — it self-hides via its own `if (!isEdit) return routeSelectionModal`
- two edit-gates required (`editPageMode` AND the section's own `isEdit`), not either alone
- route content lives in the report's own `reports_snap_2` row — no Publish/Discard semantics, ever
- route names must stay unique (comparison-series' sole series discriminator)
- derived dates are single-hop only (a derived route can't itself be a base)

   - Note: the mockup's later Phase-12 commentary (in `npmrds-report.html`) says the *rail's own* edit toggle was removed so route controls are "always live," independent of page edit mode — that's a Phase 3 (RRL) question, not touched here, and is a real tension with `ReportRouteList/README.md`'s documented two-gate constraint worth resolving explicitly when Phase 3 starts (flagging per "flag standing-decision reversals, don't reconcile quietly" — not resolved silently either way).
   - **Two real bugs found by Ryan live-checking this, both fixed 2026-08-06:**
     1. **Draft/published pill always showed "draft."** My check was `item?.published === 'published'` — a value that never occurs anywhere in the codebase. Read the actual state machine in `editFunctions.jsx`: `published: 'draft'` means pending unpublished changes (set at page creation); `published: ''` (empty) means clean/published — set by both `publish()` and `discardChanges()`. Fixed to `item?.published !== 'draft'`, matching the exact idiom already used elsewhere (`editPane/index.jsx`, `pagesPane.jsx`: `item.published === 'draft'` for `hasChanges`). Re-verified live: pill now correctly reads PUBLISHED, bottom toolbar shows "NO CHANGES."
     2. **Empty rail space in view mode** — a real, pre-existing gap Ryan found, unrelated to the Phase-1 mechanism itself but directly exposed by it (the new 340px white flush rail made empty space much more visible than the old subtle style). Root cause: `sectionGroup.jsx`'s `showRail` was computed purely from `item.sidebar` being truthy, with zero awareness of whether the sidebar group's content (`ReportRouteList`) actually renders anything — RRL's own recent fix (`if (!isEdit) return routeSelectionModal`, documented in `dynamic-reports-and-route-tags.md`'s "View-mode visibility" section) returns `null` in view mode for a normal report, but the rail's fixed-width wrapper doesn't know that and renders anyway.
        - **First attempt (WRONG, caught by Ryan same session): `showRail = ... && (edit || !item?.sidebarHideInView)`.** This gates the rail at the JS/React level — when the flag is on and we're outside edit mode, the entire rail (including `SectionArrayComp`, which is what mounts `ReportRouteList`) never renders at all. That silently swallows RRL's Dynamic-Report entry-gate modal exactly like the *original* generic `hideInView` bug already fixed once (same doc, same section) — RRL never gets a chance to decide "actually I need to show the picker." **Ryan caught this live**: toggled the NY-9D Beacon report into a Dynamic Report, published, viewed — no modal. Confirmed by direct test (below) that this was a real regression from my flag, not a "converting an existing report" artifact.
        - **Fix: collapse via CSS `:has(...:empty)`, not a JS-level gate.** `showRail` is back to the original `Boolean(item?.sidebar) && group.name === railGroupName` (rail — and therefore RRL — always mounts). A new `collapseRailIfEmpty = Boolean(item?.sidebarHideInView) && !edit` instead adds `has-[.dms-rail-content:empty]:hidden` to the rail wrapper's className, and `sideNavContainer3` gets a `dms-rail-content` marker class. This only visually collapses the rail's width/chrome once RRL has actually rendered nothing (a real empty DOM, checked after render) — RRL still always mounts, so it can still render its entry-gate modal when needed. That modal is a `createPortal(..., document.body)` (`ui/components/Modal.jsx`), so it displays fully regardless of the (possibly CSS-collapsed) rail wrapper's own visibility.
        - **Verified live, both cases, on the demo page** (temporarily added/removed a `routeSlots`-typed `item.filters` entry to switch it between Dynamic/normal — the exact mechanism `ReportRouteList.jsx`'s "Dynamic Report" toggle itself writes, then restored the page's original filter state after): (1) Dynamic Report, no `?routes=` → the "Add Routes" blocking modal now shows correctly. (2) Normal report (or resolved Dynamic Report) → rail fully collapses, content reflows full-width, no empty space. (3) `/edit/...` → full rail, unaffected, in both cases.
